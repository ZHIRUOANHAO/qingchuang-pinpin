## C1【待验证】案例详情页 3D 模型不随页面滚动

**现象**：在案例详情页上下滑动页面时，3D DNA 模型「钉」在屏幕上不动，还会盖住下方内容。真机可复现。

**两层成因（2026-09-27 补充查证）**：

**第一层——代码自己把页面滚动关掉了（已修，见下）**。canvas 的 `disable-scroll` 官方定义是「当在 canvas 中移动时且有绑定手势事件时，禁止屏幕滚动以及下拉刷新」。而 `.viewport` 高 50vh（约半屏），手指很容易落在模型上——一落上去整页就滚不动，观感正是「模型固定在那里、不随我滑动而动」。

**第二层——同层渲染是否生效（环境决定，代码改不了）**。官方原文：`<canvas>` 属原生组件，「当前所有原生组件（除 input 组件 focus 状态）均已支持同层渲染」；「同层渲染是为了解决原生组件的层级问题，在支持同层渲染后，原生组件与其它组件可以随意叠加，有关层级的限制将不再存在」。也就是说**同层渲染生效时，canvas 本来就该随页面滚动**。若它没生效，canvas 会退回「原生悬浮层」：按屏幕坐标绘制、不参与重排、层级压过普通 view。失败原因由官方点名：Android 端缺同层渲染所需内核、iOS 端在页面节点树不稳定时存在失败率。**这种情况改代码无解**，只能换渲染方案。

**2026-09-27 已完成改动**（限 `mode === 'dna'`，首页 `universe` 一字未动）：

1. `space-scene.wxml`：两个 canvas 的 `disable-scroll` 由写死 `true` 改为 `{{mode !== 'dna'}}`——`universe` 仍为 `true`，`dna` 放开。
2. `space-scene.wxml`：`catchtouchmove` → `bindtouchmove`。（官方限制原文：原生组件只支持 `bindeventname`，**不支持 catch 和 capture 事件绑定**；要让页面滚动就不能用 catch。）
3. `space-scene.js`：`onTouchMove` 增加 `dna` 专用方向锁——第一帧定方向，竖向手势整段让给页面滚动、不旋转模型，横向手势才旋转；`gestureAxis` 在 `onTouchStart` / `onTouchEnd` / `onTouchCancel` 全部复位。

改动仅 2 个文件，验证：`npm test` → 结构校验 185 通过 / 逻辑 11 通过 / 0 失败。

2026-09-28 补充：修正了仍要求 `catchtouchmove` 的过时原生界面测试，并新增竖滑不旋转、横滑可旋转的回归测试；`npm run test:native-ui` 17/17 通过。此项仍需真机确认 canvas 是否随页面一起滚动。

**验收方法（一次 10 秒的自查，能直接判定是哪一层成因）**：在案例详情页——

- 手指落在**正文文字**上上下滑 → 页面滚动，模型跟着一起上移 = 同层渲染正常。此时若「落在模型上滑不动」已消失，本条即算修好。
- 手指落在**模型**上上下滑 → 应当由页面滚动（这是本次改动的目标）。
- 若上述两种滑法里模型都死死钉在屏幕同一位置不动，说明是第一层之外的**同层渲染失败**，需改走「非 canvas 渲染」方案，请反馈后另行处理。

**⚠️ 硬约束（踩过的坑）**：`space-scene` 组件被两处复用——`pages/home/home.wxml` 的 `mode="universe"`（首页星球，页面本身不滚动，无此问题）和 `dna-view` 的 `mode="dna"`（挂在 `case-detail` / `ai` / `canvas` 三个页面）。2026-09-21 我直接改组件、没区分 mode，导致首页 canvas 脱层、案例列表排版塌掉，已被用户当场发现并全部回退。**改这个组件前必须先列出全部使用处，逐处评估。**

**已排除的方案**：
- 滚动期静态快照跟随（`toDataURL` 替换 canvas）——用户否决，切换瞬间有跳变，达不到「像淘宝那样丝滑」的要求。
- 全站切 Skyline 渲染——Skyline 不支持页面全局滚动（须改 `scroll-view`），且 canvas 在开发者工具无法调试（需 Nightly），`threejs-miniprogram` 的兼容性无任何资料佐证。

## C3【已修复】资产卡被重复构造两遍

**现象**：`data/cases.js` 的 `buildCase()` 里同时调了两个函数：

```js
const businessStages = source ? composeBusinessStages(source) : []
const businessNodes = source ? buildBusinessNodes(source) : []
```

而 `buildBusinessNodes()` 内部**又调用了一次 `composeBusinessStages()`**——于是同一个案例的 7 张阶段资产卡被完整构造了两遍。

**性质**：纯性能问题，零行为风险。案例模块加载时，100 条案例 × 7 关会多构造一遍；并非每次进详情都重算。

**修复方向**：让 `buildBusinessNodes()` 接收已算好的 stages 作为参数，或在 `buildCase()` 里复用同一个结果。

**2026-09-28 修复与验证**：`buildCase()` 把已构造的 `businessStages` 传给 `buildBusinessNodes()`；独立调用仍保留默认构造能力。测试确认全部 100 条案例的节点直接复用同一张资产卡对象。

## C4【已修复】三套节点 id 词汇互不相通（评分真 bug）

**现象**：同一个「商业阶段」概念，工程里存在**三套不同的 id 命名**：

| 出处 | id 序列 |
|---|---|
| `data/modules.js` | `exposure / traffic / nurture / conversion / transaction / delivery / retention / referral / profit / risk`（**10 个**） |
| `config/business-stages.js` | `positioning / acquisition / nurture / conversion / payment / delivery / retention`（**7 个**） |
| `data/cases.js` 的 `nodeTypes` | `exposure / traffic / nurture / transaction / delivery / risk / profit`（**第三套，7 个**） |

三套里只有 `nurture / conversion / delivery / retention` 是对得上的。

**为什么这是疑似 bug 而不只是重构**：`utils/scoring.js` 的 `CORE_TYPES` 只认特定的几个类型，从案例详情走出来的节点进评分函数时**可能匹配不上**。`pages/canvas/canvas.js` 里那句 `type: node.type || node.id` 的兜底**恰好把这个差异盖住了**——所以自动化测试是绿的，但逻辑是虚的。

**性质**：属**行为变更**，不是纯重构。统一 id 会改变评分结果和画布模块归属。

**修复方向**：先定按哪一套词汇为准（建议以 `config/business-stages.js` 的七阶段为准，因为它对应固定的「卖点定位 → 引流获客 → 种草教育 → 转化成交 → 收款 → 产品交付 → 复购裂变」链路），再统一另外两处，并补测试锁定 `CORE_TYPES` 的匹配。

**2026-09-28 本地核查**：首条案例的原始节点送入旧评分得 75%，七阶段展示节点得 88%，但后者只有部分类型被旧 `CORE_TYPES` 识别。评分确有词汇不一致问题。

**2026-09-28 修复与验证**：采用七个可见商业阶段作为结构覆盖的唯一口径，同时兼容旧模块和已保存的案例节点。案例详情和案例演示写入画布的是用户实际看到的七个节点；旧记录、方案和验证页在读取时重算分数。结构覆盖不再被多余节点冲过 100%，缺口显示中文。案例成本与风险尚未经逐案核实时显示「待核算／待评估」，不会把缺失数据当成 0 或让它通过无提示的验证入口。新增兼容和持久化测试，`npm test` 201 项结构检查、15 项体验测试通过。
